Decision-Tree Spec v0.1
Mermaid + canonical node model

The whole flow, as a directed graph a UX programmer can build.

One source of truth: every screen is a node with an ID, a type, its on-screen copy, and its outbound edges with conditions. The diagrams below are rendered from the same model that powers the node registry and the copy-ready JSON at the bottom. Node IDs are stable across all three so nothing drifts during handoff.

What this is for engineering, said plainly. Treat this as a guided-information state machine, not a legal engine. Nodes route a user and surface the right form and timeline; they never decide the merits. Two backends exist: tribunal nodes act on CJTS (the user self-logs in), court nodes act on eLitigation via a physical Service Bureau (the user cannot file online). Build the Service Bureau dependency in early; it is a hard constraint, not a detail. Re-verify every form number and statutory period against the live court sources before release.
01

How to read the model

Seven node types, a small set of state variables, and a single edge convention. If you implement these primitives, the rest is data.

Node types
question

Presents options to the user. Each option writes a value to a state variable and points to one target node.

router

No user input. Evaluates collected state against ordered rules and forwards to the first match.

action

User does something concrete (file, serve, pay). Usually carries a form reference and a system (CJTS or eLitigation).

branch

Forks on an external event or deadline (the other party responds, a window lapses), not on user choice.

subflow

A reusable module callable from many nodes (substituted service, appeal, offer to settle). Returns to caller.

terminal

End state. Tagged with an outcome class (bull / base / bear) so the UI can frame expectations.

info

Guidance-only screen with a single continue edge. No decision, no write.

State variables (collected in triage, read everywhere)

  • nature — money | consumer | salary | neighbour | harass | declaration
  • valueBand — le20k | b20_60k | b60_250k | gt250k | nonmoney
  • partyLocation — sg | outside
  • track — derived: SCT | ECT | CDRT | PHC | OC | OA
  • court — derived for OC/OA: MC | DC | HC
  • sctEligible, withinLimitation, protocolApplies — booleans
  • defendantResponded, defenceFiled, assetsKnown — event flags

Edge convention

  • Every node has edges: [{ when, to }].
  • when:"always" for single-exit nodes.
  • question edges mirror options[].value.
  • router rules are ordered; first true wins; include a default.
  • subflow nodes have returns:true and resume the caller.
  • Targets prefixed END_ are terminals; SF_ are subflows; X* is enforcement.

06
Build notes for the UX programmer
The non-obvious things that will bite if missed, including where this cuts against a naive "just file it" UX.

    

      
Two backends, not one
    
        
  • Tribunal nodes (S*, E*, C*, H*) deep-link into CJTS; the user authenticates and acts there.
    • 
        
  • Court nodes (O*, A*, X*) cannot file online. Model the Service Bureau as a real-world step: generate a print pack, then a "go to bureau" checkpoint with appointment booking.
    • 
        
  • Never imply the app files to eLitigation directly for a self-litigant. It cannot.
    • 
      

      
Timers are first-class
    
        
  • branch nodes (O7, O8, A5, X4) hang on deadlines. Store served-on dates and compute windows (14 / 21 days, 21 days / 5 weeks, 3-month OC validity, 12-month EO).
    • 
        
  • Different clocks for service in vs out of Singapore. Drive these off partyLocation.
    • 
        
  • Surface countdowns and the consequence of lapse (default judgment for, or against, the user).
    • 
      

      
Forms are data, not constants
    
        
  • Each action node references a form by stable key, not a hard-coded number.
    • 
        
  • Form numbers shift with Practice Direction updates; resolve keys against a live forms table at runtime.
    • 
        
  • Flag any form the user must draft themselves (pleadings) versus fill in a template; the bureau will not draft.
    • 
      

      
Honest guardrails
    
        
  • No node should output merits advice. Gate trial-stage nodes (O10) behind a "consider getting advice" interstitial.
    • 
        
  • Terminals carry an outcome class (bull / base / bear) so the UI sets realistic expectations, especially that a judgment is not recovery (X1 to X6).
    • 
        
  • Route specialist matters (probate, insolvency, family, IP, admiralty) to an off-ramp; they are out of scope and mis-filing them harms users.
    • 
      

    

    
One contrary note worth surfacing in the product itself. The cleanest UX would hide the Service Bureau friction, but doing so would mislead. The honest design makes the in-person, no-legal-advice constraint visible at the OC and OA entry points, and positions the SCT and tribunal tracks (which a person can genuinely complete alone online) as the recommended path whenever a dispute qualifies for them.
